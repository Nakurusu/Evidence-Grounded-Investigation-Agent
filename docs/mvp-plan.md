# MVP Completion Plan

## Product position

当前项目已经具备调查型分析引擎的主干：上传结构化数据后，系统可以完成数据画像、信号检测、问题生成、假设生成、证据生成、假设验证、结构化报告、LLM 叙事和后续调查建议。

MVP 的目标不是继续扩大功能数量，而是把这条链路打磨到一个用户可以信任、可以理解、可以围绕业务问题使用的状态。当前阶段应先完成单数据集调查体验，再继续推进多数据集分析和更复杂的交互式调查。

## MVP definition

MVP 应该支持两种使用方式：

- 探索驱动：用户上传数据集，系统告诉用户哪些风险、异常或机会值得关注。
- 问题驱动：用户上传数据集并输入一个业务问题，系统围绕这个问题组织信号、假设、证据和报告。

MVP 的核心输出应回答：

- 发生了什么。
- 哪些信号值得调查。
- 可能有哪些解释。
- 哪些证据支持或反驳这些解释。
- 当前结论有多可靠。
- 下一步应该查什么数据或问题。

## MVP expected state

### 调查问题输入

用户上传数据时可以输入一个可选业务问题，例如"为什么收入下降"或"哪些地区表现异常"。系统保存该问题，并让 pipeline 读取它影响报告上下文和 findings 排序。如果用户不输入问题，系统按探索驱动模式运行。

### 问题驱动的信号和发现排序

问题进入系统后，系统用保守的方式影响排序和展示：

- 如果问题中出现某些字段名或字段别名，相关 signal 和 finding 优先展示。
- 如果问题包含"下降、增长、异常、缺失、集中、波动"等词，相关 signal type 优先展示。
- 不过滤掉其他发现，只改变优先级和报告呈现顺序。
- 排序逻辑可追踪，不让 LLM 改变确定性结论。

### 语义字段角色

字段画像从基础类型扩展到分析角色。MVP 支持第一批角色：

- metric：可分析的数值指标。
- dimension：可分组的类别字段。
- time：主要时间字段。
- entity：客户、产品、订单等实体标识。
- identifier：纯标识符，不直接作为分析维度。

趋势分析使用 time 字段。集中度分析优先使用 dimension × metric。identifier 不再被误当成普通分析维度。

### 原因候选排序

报告中包含 3 到 5 个原因候选，基于已验证的 findings 生成排序结果。每个候选包含支持证据、限制说明和下一步验证建议。排序采用确定性评分：

- 支持证据数量越多，分数越高。
- 高置信度 finding 分数更高。
- 与用户问题相关的 finding 分数更高。
- 有反驳证据或数据质量限制时降低分数。
- 多个信号共同指向同一解释时提高分数。

候选原因不表述为确定因果。

### 可运行的后续调查

交互式调查支持至少 3 类 follow-up question 对应到可运行的 drill-down。MVP 最终支持 6 类：

- 查看异常值或尾部记录摘要（outlier、right_skew、left_skew）。
- 按主要维度拆解趋势（increasing/decreasing trend）。
- 比较头部类别与其他类别（high_concentration）。
- 检查缺失值是否集中在某些维度（high_missing_rate）。
- 查看值频率分布（high_cardinality）。
- 低方差分布统计（low_variance）。

后续分析返回新的 evidence 或 summary。原始报告不被覆盖，而是追加一个 investigation step。

### 前端流程

前端围绕"问题、发现、证据、原因候选、下一步调查"组织，而不是只展示后端对象结构。

页面结构：

- 上传页：文件 + 可选调查问题。
- 等待页：当前阶段、阶段目的、输入、输出、为什么需要这一步。
- 总览页：调查问题、核心发现、原因候选、整体置信度。
- 发现页：每个 finding 的证据、方法、阈值、限制。
- 后续调查页：可继续追问的问题和数据缺口。

用户不需要理解内部 pipeline，也能看懂系统结论。技术证据仍然可以展开查看。中文界面不混杂硬编码英文。

## MVP non-goals

以下内容不在 MVP 范围内：

- 完整多数据集根因图谱。
- 自由对话式分析代理。
- 自动生成复杂图表仪表盘。
- 让 LLM 直接生成或修改统计结论。
- 大规模性能优化。
- 多租户、权限、审计等生产级平台能力。

## MVP completion signal

当用户能完成下面这条路径时，可以认为 MVP 成立：

1. 上传一个业务数据集。
2. 输入一个问题，例如"为什么收入下降"。
3. 等待页解释系统正在做什么。
4. 总览页给出与问题相关的核心发现。
5. 报告列出 3 到 5 个原因候选，并说明证据和限制。
6. 用户可以选择至少一个后续问题继续分析。
7. 系统不会把相关性说成确定因果。

达到这个状态后，再继续推进 Phase 9 多数据集分析和更完整的交互式调查，会更符合项目愿景。

## Milestone status

| Milestone | Content | Status |
|---|---|---|
| 1. Question-aware investigation | 调查问题输入、任务保存、报告展示和基础排序 | Completed |
| 2. Semantic profiling | 字段角色识别（metric、dimension、time、entity、identifier） | Completed |
| 3. Cause candidates | 原因候选排序，3–5 个解释 + 证据 + 限制 | Completed |
| 4. Runnable follow-ups | 6 类 drill-down 分析，可点击运行，结果追加到报告 | Completed |
